# Engineering decisions

Short records of the significant choices, why they were made and what they cost. Newest last.

---

## ADR-001 — Modular monolith, not microservices

**Context.** One developer, a small codebase, and a core operation (a transfer) that must atomically update two accounts, a ledger and an idempotency record.

**Decision.** One Spring Boot application with one PostgreSQL database. New modules are feature packages: `com.example.ebank.transfer` holds its entities, repositories, service, controller and DTOs. The original layer packages (`web`, `services`, `entities`…) are migrated when they are next substantially changed, not in a big-bang refactor.

**Consequences.** A transfer is a single ACID transaction instead of a distributed saga. Scaling is vertical or by running identical instances behind a load balancer. Module boundaries are enforced by package discipline, not network calls.

---

## ADR-002 — PostgreSQL instead of MySQL; Flyway owns the schema

**Context.** The project used MySQL 8.1 (a short-lived "innovation" release), the schema was generated by Hibernate `ddl-auto=update`, and nothing created tables in Docker. There was no data to preserve. The developer already runs PostgreSQL locally.

**Decision.** PostgreSQL 18, with the schema defined by versioned Flyway migrations (`src/main/resources/db/migration`). Hibernate runs with `ddl-auto=validate`, so the application refuses to start if entities and schema disagree.

**Consequences.** The schema is reviewable SQL with named constraints, check constraints and composite foreign keys. Integration tests use the same engine and version (Testcontainers `postgres:18-alpine`). Every schema change now needs a migration file. Existing MySQL data was intentionally discarded.

---

## ADR-003 — Money as `BigDecimal` / `NUMERIC(19,2)`, currency per account, no silent rounding

**Decision.** Amounts are `BigDecimal` in Java and `NUMERIC(19,2)` in the database. Each account has an ISO 4217 currency from a configured list (MAD, EUR, USD). An amount with more decimals than the currency allows is rejected (400 `INVALID_AMOUNT_SCALE`), never rounded. A database check constraint forbids negative balances.

**Why.** `double` cannot represent most decimal fractions (`0.1 + 0.2 = 0.30000000000000004`). Rounding silently changes what the user asked for.

**Consequences.** Transfers (Phase 2) will only be allowed between accounts of the same currency; there is no FX.

---

## ADR-004 — Errors as RFC 7807 problem details with stable codes

**Context.** In a real container every error, including "no such endpoint", came back as `403` with an empty body. The `/error` forward was itself subject to authentication.

**Decision.**
- A single `@RestControllerAdvice` produces `application/problem+json` with `status`, `detail` and a stable machine-readable `code`; validation errors add an `errors` map.
- Security's entry point and access-denied handler delegate to the same advice.
- The `ERROR` dispatch is permitted.
- Status codes: 400 validation, 401 unauthenticated / invalid credentials, 403 wrong role, 404 not found (including other tenants' resources), 409 conflicts, 500 unexpected errors (logged, never detailed to the client).

**Consequences.** The frontend can show precise messages and distinguish "session expired" (401) from "forbidden" (403).

---

## ADR-005 — Tenant column from day one, resolved from the authenticated user

**Decision.** `organization_id` exists on users, clients and accounts from the first migration, with one seeded organization ("Demo Bank"). The caller's organization is loaded from the database on every request and is never accepted from the request body or headers.
- Tenant-owned lookups are scoped in the repository query (`findByIdAndOrganizationId`).
- Another organization's resource is reported as 404, not 403, so its existence is not revealed.
- A composite foreign key `(client_id, organization_id)` makes it impossible at the database level to attach an account to a client of another organization.

**Consequences.** Cross-tenant tests exist before multi-tenant features do. Organization management (onboarding, admins, plans) is still Phase 5+.

## ADR-006 — Server-generated synthetic RIBs with check digits

**Decision.** Account identifiers are generated by the server: `EB` + 2 check digits + 20 random digits, using the IBAN ISO 7064 MOD 97-10 scheme. Callers cannot choose them.

**Why.** Free-text identifiers caused duplicates and unhandled errors. Check digits detect any single-digit typo in a recipient number before a lookup, which matters once clients can transfer to any account. The `EB` prefix makes clear the identifiers are synthetic, not real bank details.

## ADR-007 — Onboarding credentials: unique one-time password, email as username

**Context.** Every client received the hard-coded password `client123`, and usernames were the email local part, so different addresses could collide.

**Decision.** The username is the full, lower-cased email. Each onboarded client gets a random 96-bit temporary password, returned once to the agent in the onboarding response and stored only as a BCrypt hash. The demo agent is created only under the `demo` profile, with a password from configuration (no built-in default).

**Follow-up (Phase 3).** Force a password change at first login.

## ADR-008 — Session token in an HttpOnly cookie, with CSRF protection

**Status.** Implemented in Phase 3. It replaces the Phase 1 bearer token in `localStorage`.

**Problem.** A token readable by JavaScript is stolen by any XSS bug. A cookie the browser sends automatically opens the door to CSRF instead.

**Decision.**
- **Cookie:** the JWT lives in `EBANK_SESSION`, which is `HttpOnly`, `Secure`, `SameSite=Strict` and `Path=/api`, and lasts as long as the token. The login response body no longer contains the token.
- **CSRF:** Spring Security's `csrf().spa()` double-submit pattern.
  - The SPA calls `GET /api/auth/csrf` at startup.
  - Axios copies the readable `XSRF-TOKEN` cookie into an `X-XSRF-TOKEN` header on writes (same-origin only).
  - The token is BREACH-safe (XOR-masked when rendered).
  - Login is CSRF-protected too.
- **API clients** may still send `Authorization: Bearer`. Such requests skip CSRF, because browsers never add that header on their own. The filter **never falls back to the cookie** when an Authorization header is present, so the exemption cannot be abused (a mutation test proves it).
- **Session restore:** the SPA asks `/api/auth/me` on load. Nothing is stored in the browser.

**Consequences.** XSS can no longer exfiltrate the token, though it can still act within the page; the CSP (ADR-014) reduces that risk. There are no refresh tokens: when the session expires, the user logs in again.

**Lesson (verified in a real browser).** Browsers send `Origin` on every POST, even same-origin ones. Nginx was forwarding `Host` without the port, so Spring saw `localhost:80` and rejected `Origin: http://localhost:3000` as cross-origin ("Invalid CORS request"). curl and MockMvc never send `Origin`, so this went unnoticed until headless Chrome was used. The fix: forward `$http_host` and `X-Forwarded-Port`.

## ADR-009 — Vite instead of Create React App

**Context.** Create React App is deprecated. It accounted for most of the 105 `npm audit` findings, including 3 critical ones.

**Decision.** Vite for dev server and build, Vitest + Testing Library for tests, ESLint flat config. The app stays in JavaScript. The dev server proxies `/api` to the backend, so development is same-origin like production and needs no CORS.

**Result.** `npm audit` reports 0 vulnerabilities with the new toolchain (measured 2026-10-12).

## ADR-010 — Ledger as source of truth, stored balance as a transactional cache

**Context.** A transfer must be auditable and every balance explainable, but reading a balance should stay a single-row read.

**Options.**
1. Balance only: no audit trail.
2. Derive the balance from the ledger on every read: correct, but reads get slower as history grows, and checking for overdraft needs an aggregate under lock.
3. **An append-only ledger plus a stored balance updated in the same transaction.**

**Decision.** Option 3.
- `ledger_entry` rows are `DEPOSIT`, `DEBIT` or `CREDIT`, always with a positive amount and the account's running `balance_after`.
- Each transfer writes exactly one DEBIT and one CREDIT of the transfer amount.
- `bank_account.balance` is a cache of `Σ(DEPOSIT + CREDIT) − Σ(DEBIT)`, maintained in the same transaction.
- `LedgerEntryRepository.findUnreconciledAccountIds()` must always return nothing; the tests assert this after every scenario, including the concurrency tests.

**Append-only.** Entities are `@Immutable`, and PostgreSQL triggers reject any `UPDATE` or `DELETE` on `transfer` and `ledger_entry`, even from a SQL console. Corrections, if ever needed, will be new compensating transfers.

**Simplification, stated openly.** Deposits are single-sided entries: simulated money enters the system, and there is no "bank cash" counter-account. A full double-entry chart of accounts would add a system account per organization and currency; that is not useful at this scale. The double-entry invariant therefore holds **per transfer**, not globally.

## ADR-011 — Concurrency: pessimistic row locks in a global order

**Problem.** Two concurrent transfers from the same account can both read balance 100 and both debit 80. That is a lost update, or a negative balance.

**Options.**
- Optimistic locking (`@Version`) with retries: no waiting, but hot accounts produce retry storms, and the code needs a retry loop.
- A conditional update (`UPDATE … SET balance = balance - x WHERE balance >= x`): fast, but the credit side and the ledger's `balance_after` still need care.
- **Pessimistic locks (`SELECT … FOR UPDATE`)**: concurrent transfers on the same account queue up; business rules are evaluated on locked, current data.

**Decision.** Pessimistic locks on both accounts, always acquired in ascending account id order. A transfer A→B and a transfer B→A then lock in the same order, and cannot deadlock.

**Pitfall avoided.** The pre-lock checks (ownership, recipient lookup) use `exists` and id-only queries. If a `BankAccount` entity were already loaded in the persistence context, Hibernate would return that stale instance from the locking query: the row would be locked, but the balance in memory would be old.

**Evidence.** `TransferConcurrencyTest` runs on real PostgreSQL. Each guarantee was checked by deliberately breaking the code:
- Without the lock, 20 of 20 transfers of 10 succeeded from a 100.00 account (expected exactly 10).
- Without the id ordering, PostgreSQL reported `deadlock detected`.

**Trade-off.** Transfers touching the same account are serialized: throughput per account is bounded, which is the correct behaviour for a balance. Transactions are kept short, with no remote calls inside.

## ADR-012 — Idempotency-Key for transfer creation

**Problem.** A client that times out cannot know whether its transfer happened. Retrying blindly could pay twice.

**Decision.** `POST /api/client/transfers` requires an `Idempotency-Key` header. The SPA generates a random key per transfer attempt, keeps it for retries of that attempt, and generates a new one when the user edits the form.
- The key is stored on the transfer row, with a unique constraint on `(initiated_by_id, idempotency_key)`, and a SHA-256 hash of the canonical request.
- Same key, same payload → the original transfer, with `200` and `Idempotent-Replayed: true`. The first call answered `201`.
- Same key, different payload → `422 IDEMPOTENCY_KEY_REUSED`.
- Concurrent retries with the same key queue on the account lock. The key is looked up again after the lock is acquired, so all but one get the replayed result; the unique constraint is the last line of defence.

**Limits.**
- Only successful transfers are stored. A retry of a *rejected* request (for example, insufficient funds) is evaluated again, which is the useful behaviour once funds arrive.
- Keys never expire (no cleanup job yet).
- A key reused at the same instant for different source accounts surfaces as `409 DATA_CONFLICT`.

## ADR-013 — Synchronous transfers, no status column

**Decision.** Transfers are executed within the HTTP request. A `transfer` row exists only for a completed transfer; a failed one leaves no rows and no balance change (verified by a forced-failure test after the debit has been flushed).

**Why.** There is no asynchronous step (no external payment network) that would justify `PENDING` states, queues or sagas. If reversals or scheduled transfers are added later, a status, or a separate reversal transfer, will be introduced with them.

## ADR-014 — Session revocation, first-login password change, Content-Security-Policy

**Revocation.** Each user has a `token_version`, copied into the JWT as `ver`. The filter rejects tokens whose version is older than the user's.
- Logout and password change increment it, which signs the user out **on every device**. Coarser than per-token revocation, but stateless and simple.
- Disabling a user is effective immediately, because the user row is read on every request.

**First login.** Clients onboarded with a one-time password have `must_change_password`. While it is set, the filter authenticates them **without any role**: only `/api/auth/me`, `/api/auth/password` and `/api/auth/logout` work, and everything else answers `403 PASSWORD_CHANGE_REQUIRED`. The SPA redirects to the change-password page, but the server-side block is what matters.
- **Policy:** 12 to 64 characters, at most 72 bytes (BCrypt's limit), different from the current password, and must not contain the email's local part.
- A wrong current password is a `400`, not a `401`, so the client does not mistake it for an expired session.

**CSP.** `default-src 'self'; script-src 'self'; style-src 'self'; …; frame-ancestors 'none'`, set by Nginx on every SPA response. The pages' inline `<style>` blocks were moved to CSS files to make that possible. React's `style={{…}}` props are applied through the DOM (CSSOM), which CSP does not block. Verified in headless Chrome: no violations in the full scenario.

## ADR-015 — Login throttling

**Decision.** A sliding window of failed password checks (login and password change):
- 5 per username or 20 per client IP within 15 minutes.
- Above either limit, attempts are refused with `429 TOO_MANY_ATTEMPTS` and `Retry-After`, **even with the right password**; otherwise an attacker learns when they guessed it.
- A success clears the username's counter.

**Client IP.** Nginx **overwrites** `X-Forwarded-For` with the connecting address, and Tomcat trusts it only from private-network proxies (`forward-headers-strategy: native`). A spoofed header was verified to be ignored.

**Trade-offs.**
- A per-username limit lets an attacker lock a victim out for 15 minutes; the short window bounds that denial of service.
- State is in memory, per instance, and reset on restart. A multi-instance deployment would need a shared store.
- Locally, every host request reaches Nginx from the Docker gateway, so all local users share one IP bucket.

## ADR-016 — Audit trail

**Decision.** An append-only `audit_event` table, protected by an `@Immutable` entity, a trigger, and no UPDATE/DELETE grant. It records logins (success, failure, throttled), logout, password changes, onboarding, account opening and transfers, with actor, organization, target, client IP and short non-secret details. Agents read their organization's trail through `GET /api/admin/audit-events`.

**Transaction semantics.**
- Business events join the business transaction, so a rolled-back transfer leaves no "completed" event.
- Security events of failing operations (a failed login) are committed independently (`REQUIRES_NEW`), so the failure is recorded even though the request throws.

**Not recorded.** Passwords (temporary or chosen), tokens, request bodies. A test asserts this.

## ADR-017 — Least-privilege database access

**Decision.** Two roles.
- **Owner:** Flyway migrates as the schema owner (`POSTGRES_USER`).
- **Application:** the app connects as `ebank_app`, created by a Docker init script. Migration V3 grants it data access only:
  - SELECT/INSERT/UPDATE/DELETE on ordinary tables, but **only SELECT/INSERT** on `transfer`, `ledger_entry` and `audit_event`;
  - no DDL;
  - no access to `flyway_schema_history`.

**Why.** Even a successful SQL injection could not drop tables, disable the append-only triggers, or rewrite the ledger and audit history.

**Evidence.** The whole integration test suite runs as `ebank_app` against PostgreSQL. A dedicated test checks that `DROP TABLE`, `ALTER TABLE … DISABLE TRIGGER`, `CREATE TABLE`, deleting audit rows and reading Flyway history are all refused. The append-only test checks both layers (no grant for the app, triggers for the owner).

**Operational note.** The init script only runs when the database volume is created. An existing Phase 1/2 Docker volume must be recreated (`docker compose down -v`, which deletes its demo data). In local development, connecting as `postgres` for both roles skips the grants (the V3 block detects it).

## ADR-018 — Frontend structure: app shell, one stylesheet, small shared primitives

**Context.** Pages had grown independently, each with its own inline styles, header and loading logic, plus two visual themes. Agents needed numeric ids to work.

**Decision.**
- **Layout and styles:** one `AppShell` layout (skip link, header with role-based navigation, `<main>`, footer) for every signed-in page. One stylesheet with colour tokens (`styles/app.css`), so contrast is reviewed in one place.
- **A few in-house primitives instead of a UI library:**
  - `PageHeader` updates the document title and moves focus to the page heading after each navigation, so screen-reader users hear the new page.
  - `useQuery` exposes a derived loading state, and an answer to an outdated request is ignored.
  - `ConfirmButton` is an inline two-step confirmation: no modal and no focus trap to get wrong.
  - `Pagination` and `StatusBadge`.
- **Routing:** nested routes, `/admin/*` for agents and `/client/*` for clients, each guarded by role. The backend enforces the same rules independently.

**Why no component library.** The app has about ten pages. A library would add weight and a theming layer to learn, for little gain. Revisit if the UI grows significantly.

**Verification.** axe-core in headless Chrome reports zero violations on all eight pages, and pages are usable at 375 px. One real bug was found this way: an absolutely positioned `.sr-only` table header escaped its scroll container and widened the page on phones.

## ADR-019 — Multi-tenancy: shared schema, four roles, isolation enforced twice

**Model.** One database and one schema, with `organization_id` on every tenant-owned row (ADR-005). The tenant is always the authenticated user's organization, loaded from the database on every request.

**Roles.**
- **`PLATFORM_ADMIN`** has no organization. It creates organizations (each with its first admin, in one transaction) and suspends or reactivates them. It sees counts only, never customers or money: least privilege for the operator.
- **`ORG_ADMIN`** manages one organization's staff, sees an overview, and reads the audit trail. It does not operate accounts; that is the agents' job (separation of duties).
- **`AGENT`** and **`CLIENT`** are unchanged.

**Lifecycle.**
- *Suspension* keeps the data. Every user of the organization is rejected on their next request: the security filter checks the organization's status, and login reports the generic 401.
- Organizations are *created* by the platform admin only. Public self-service sign-up would need abuse protection (captcha, e-mail verification) that is out of scope; it could come with plans in Phase 6.

**Isolation enforced twice.**
1. **Application:** tenant-scoped repository queries. Another organization's resources answer 404, so their existence is not revealed. A cross-tenant matrix test covers every tenant-scoped endpoint.
2. **Database:** composite foreign keys `(x_id, organization_id) → parent(id, organization_id)`, for client→login, transfer→source/destination account, and ledger entry→account. A cross-tenant row cannot be stored even by code that bypasses the services.

**Concurrency detail.** "Never disable the last active admin" cannot be broken by a single request, since the caller is itself an active admin. It *can* be broken by two admins disabling each other at the same instant. Staff changes lock the organization row, which serializes them; a concurrency test (and its mutation check) proves it.

**Rejected alternatives.** Schema-per-tenant or database-per-tenant: stronger isolation, but migrations, connection pools and cross-tenant reporting multiply for no benefit at this scale. PostgreSQL row-level security: a valid next step for a third layer, at the cost of setting a session variable per transaction.
